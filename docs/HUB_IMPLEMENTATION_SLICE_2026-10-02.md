# TomaDesk Hub: 이번 무인 구현 범위

기준 계획: [전체 Hub 계획](TOMADESK_HUB_MASTER_PLAN.html), [Telegram 상세 계획](TOMADESK_TELEGRAM_HUB_PLAN.html).

## 범위

이번 작업은 향후 단계 1·2·3·4의 **로컬 핵심 계약**을 묶어 진행한다. 실제 Telegram 계정, Google Drive, Dot, 사용자 DB에 연결하지 않는다. 4시간은 사용자 요청의 작업 상한으로 삼되, 시간이 지났다는 이유만으로 미검증 기능을 완료 처리하지 않는다.

1. Action v1을 검증하고 출처 이벤트별 중복을 막는다. 수집함 입력과 Receipt를 하나의 DB 트랜잭션으로 기록한다.
2. Telegram 개인 대화 문자 Update를 Action으로 변환하는 순수 어댑터를 만든다. 봇·사용자·채팅 식별, 원본 전송 시각, 재시도 ID를 검증한다. 네트워크 수신기는 만들지 않는다.
3. Organizer에서 외부 원문·출처·상태를 확인하고 승인 또는 거부한다. 승인된 일정·할 일·일반 메모와 영수증은 원자적으로 저장한다. 기존 로컬 수집함의 처리 방식은 유지한다.
4. PC의 수집함·요약 화면에서 공개할 일정을 명시적으로 선택하고, 허용한 일정만 읽기 전용 Snapshot으로 만든다. 메모·본문·첨부는 내보내지 않는다. 로컬 게시 파일은 임시 파일을 완성한 뒤 교체해 실패 시 마지막 정상본을 보존한다.
5. 임시 DB의 오류 주입, 중복 재시도, 백업·복원, 기존 Organizer·모바일 브리지 회귀 테스트를 수행한다.

`pytest.ini`는 정규 `test_*.py` 파일만 자동 수집한다. 두 위치의 `memo_usability_test.py`는 직접 실행하는 시나리오 스크립트로 남기며, 같은 모듈명 충돌과 import 시 UI 실행을 전체 테스트에서 피한다.

## 완료 기준과 제외 범위

- 같은 외부 이벤트를 여러 번 받아도 수집함·일정이 한 번만 생성된다. 서로 다른 동일 문장은 각각 보존된다.
- Telegram 출처 이벤트 키에는 공개 봇 ID와 `update_id`를 함께 써서 봇 교체 후 번호 재사용도 구분한다. 봇 토큰 자체는 저장하지 않는다.
- 승인 중 오류가 나면 수집함 적용 표시·일정·Receipt가 모두 원상태로 남는다.
- 외부 정보·아이디어 승인은 네이티브 메모를 정확히 한 번 만들고, 삭제 후에도 수집함 원문은 보존한다. `확인 필요` 항목은 종류를 지정하기 전에는 적용 완료가 될 수 없다.
- 거부와 승인 결과는 재시작/백업 후에도 유지된다.
- 전체 JSON 백업에 영수증·공개 선택 기록을 포함한다. 이전 형식의 백업에는 새 테이블이 없으므로 복원 시 현재 기기의 새 테이블을 같은 트랜잭션에서 비워 오래된 기록이 섞이지 않게 한다.
- Snapshot은 기본 비공개이며 명시적으로 허용한 일정의 최소 필드만 담는다.
- 로컬 Snapshot 게시가 실패해도 이전 정상 파일의 바이트가 바뀌지 않는다.
- 저장 중인 미커밋 변경이 있으면 Snapshot 게시를 거부한다.
- 실제 Telegram 봇 배포, Drive 대기열/게시, Dot 연결, 휴대폰 실사용 검증, APK/EXE 제작, GitHub 푸시는 이번 범위가 아니다. 이 단계들을 완료로 표시하지 않는다.

## 확인할 남은 위험

- 복원된 오래된 DB를 실제 외부 대기열에 재연결할 때에는 서버 식별·영수증 기준점을 대조하고 자동 적용을 중단하는 절차가 필요하다.
- Snapshot의 실제 Drive 게시, 원격 게시 실패 시 마지막 성공본 유지, 오래된 데이터 표시와 수신·회신 운영 방식은 별도 단계다.
- Telegram 실제 수신 및 Drive 게시를 붙이기 전에 연결 계정과 권한을 확인하고, 수신 실패·게시 실패의 운영 기록과 재시도 경계를 정해야 한다.
- 현재 Snapshot의 `revision`은 공개 필드와 일정 갱신 시각에서 만든 읽기용 식별자다. 같은 분 안에 상태가 바뀌었다가 되돌아오는 경우까지 보장하는 단조 증가 revision은 아니다. 5·8단계의 완료/수정 Action을 열기 전 별도 revision·충돌 계약을 추가해야 한다.
- 후속 보완으로 전체 JSON 백업에 메모 카테고리·주석·템플릿·버전·동기화 삭제 기록을 추가했다. 전체 백업·복원 대상은 더 이상 수동 테이블 목록이 아니라 두 DB의 실제 일반 테이블에서 매번 검색하며, 외래키 의존 순서로 복원한다. 새 테이블의 자동 포함·왕복 복원과 예전 백업의 호환성은 임시 DB에서 검증했다. 현재 프로그램에 없는 테이블/열 또는 지원하지 않는 DB 테이블 형식은 조용히 누락하지 않고 실패한다. 예전 백업에는 해당 메모 데이터가 원래 없으므로 복원 화면에 누락 경고를 표시하고, 복원 직전 현재 상태를 새 형식으로 안전 백업한다. 실제 사용자 DB의 복원본 점검은 아직 수행하지 않았다.

## 단계별 완료 경계

| 원래 단계 | 이번 로컬 구현 | 아직 완료로 보지 않는 부분 |
| --- | --- | --- |
| 1. 외부 계약 | Action 검증·DB Receipt(`awaiting_review`/`applied`/`rejected`)·원자적 승인 | Drive 대기열의 `pending`/`captured`/`error`, 운영 인증·로그 |
| 2. Telegram 빠른 입력 | 개인 문자 Update 변환·허용 ID 검사 | 실제 봇 수신, 휴대폰 실사용 |
| 3. 검토·반영 | 출처 표시·승인·거부·일반 메모 저장 | Telegram 결과 회신·운영 재시도 |
| 4. Snapshot | 사용자 공개 선택 UI·최소 JSON·로컬 원자 교체 | Drive 게시·오래된 데이터 표시·오늘/D-Day 전용 화면 |

## 검증 기록

- 임시 DB를 사용하는 Hub·Organizer·모바일 브리지·복원·저장 경로의 관련 테스트: **146개 통과**.
- 전체 정규 테스트: **1,949개 통과, 15개 실패, 2개 건너뜀**. 변경 전 커밋 `68aafeb`의 실패 15개와 이름이 정확히 같았다. 마지막 종일 표시·Telegram 필드 검증 같은 작은 수정은 그 후 관련 테스트에서 다시 통과했다.
- 기본 `pytest` 수집은 `pytest.ini`를 통해 정상 동작한다. 남은 15개는 달력·편집기·OCR 등의 기존 실패이며 이 Hub 기능 완료 판정과 혼동하지 않는다.
