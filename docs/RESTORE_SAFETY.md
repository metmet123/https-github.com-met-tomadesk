# 전체 백업·복원 보호 보완 · 2026-09-19

## 해결한 문제

1. 복원 대상 DB의 필수 테이블이 빠졌거나 형식·버전·행 구조·식별자가 잘못된 백업은 기존 데이터 변경 전에 거부한다. 명시한 빈 테이블은 정상적인 빈 데이터로 복원할 수 있지만 누락 테이블과는 구분한다. 백업에 아예 없는 DB는 기존대로 보존한다.
2. 파일 DB들을 전용 연결에 ATTACH하여 하나의 SQLite 트랜잭션으로 삭제·삽입·참조 무결성 검사·커밋한다. 두 번째 DB 삽입 실패, 외래 키 오류, 커밋 거부 시 모든 DB가 함께 롤백된다. 실제 앱의 단축키 DB와 메모 DB도 같은 방식이다.
3. 복원하는 settings에 외부 AI 권한이 있거나 대상의 기존 settings에 해당 권한이 있으면 최종 값을 false로 저장한다. 백업의 허용 값으로 현재 권한이 상승하지 않는다. 외부 AI 설정을 복원하지 않는 구형 단축키 전용 백업은 현재 메모 DB와 그 권한을 그대로 보존한다. 복원 확인창에도 정책을 표시한다.

JSON 백업 저장도 임시 파일 쓰기·flush·fsync 후 교체하도록 바꿨다. 저장 실패로 기존 안전 백업 파일이 잘리는 것을 막는다. 실제 앱의 복원 직전 안전 백업도 유지한다.

## 호환성과 제한

- 현재 형식인 `sqlite-database-bundle`, 버전 1을 검증한다. 기존 `tables` 형식의 단축키 전용 백업도 지원한다.
- 행의 새 칼럼에 대한 기존 기본값·포스트잇 이전 설정 변환을 유지한다. 그러나 필수 테이블이 빠진 오래된 전체 백업은 자동으로 빈 테이블을 만들지 않고 거부한다. 그런 백업은 별도 명시적 변환이 필요하다.
- 원자적 다중 DB 복원은 파일 DB의 rollback-journal 모드(DELETE/TRUNCATE/PERSIST)를 사용한다. WAL·MEMORY·OFF 모드와 메모리 DB는 복원을 거부하며 저장 모드를 임의 변경하지 않는다. 현재 앱의 기본 SQLite 파일 DB는 지원된다.
- 저장 중인 트랜잭션이나 읽기 전용 대상으로는 복원하지 않는다. 기존 연결의 미저장 작업을 임의 커밋하지 않는다.
- 권한은 복원 성공 시에만 차단으로 바뀐다. 실패 시 설정까지 이전 상태로 롤백한다.
- SQLite 저널을 통한 복원 중 프로세스 종료 복구를 검사했다. 물리 디스크 고장이나 실제 전원 차단을 실험한 것은 아니다.

## 검증

- 복원 보호 테스트 `test_restore_safety.py`: **28 passed**.
- 기존 JSON·SQLite 백업, 구버전 포스트잇 변환, 메모 정리·패키지 검사와 연계 실행: **61 passed, 11 deselected**. UI 포스트잇 테스트는 이번 범위에서 제외했으며 해당 수치는 위 보호 테스트와 일부 중복된다. 마지막 커밋 거부 테스트는 이후 보호 테스트 28개 실행에 포함했다.
- 불완전한 구조 7종, 잘못된 버전 4종, 두 DB 제약 오류, 삽입 실패, 외래 키 불일치, 커밋 실패, WAL·읽기 전용·미저장 상태 거부, AI 권한 네 조합, 기존 백업 파일 보존을 확인했다.
- 시험용 자식 프로세스를 두 DB 변경 후 커밋 전에 즉시 종료시킨 뒤, 두 DB가 이전 데이터로 복구됨을 확인했다.
- 사용자 데이터로 복원하지 않았다. 현재 메모·일정·설정은 변경하지 않았다.
- 빌드한 EXE의 임시 DB 실행 진단 **14개 통과**, 종료 코드 0, `frozen: true`, `ok: true`. 실제 복원 실패 시나리오는 위 소스 테스트로 검증했다.
