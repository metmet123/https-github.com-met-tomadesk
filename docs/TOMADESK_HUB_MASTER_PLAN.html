01 / 비슷한 제품은 어떻게 쓰이나

다섯 가지 작동 방식에서 배울 점

제품 소개 문구보다 도움말에 적힌 실제 입력·확인·완료·동기화 흐름을 기준으로 비교했다. 아래의 “TomaDesk 적용”은 자료에서 내린 설계 판단이다.

제품
공식 자료에서 확인한 작동 방식
TomaDesk에 적용
Todoist
Quick Add + Inbox

한 줄 입력에서 자연어 날짜·라벨을 인식한다. 프로젝트를 정하지 않은 입력은 Inbox에 두고 나중에 분류·날짜를 정한다. 잘못 인식된 날짜는 일반 텍스트로 되돌릴 수 있다.

Quick Add · Inbox

Telegram 원문은 먼저 수집함에 넣고, TomaDesk가 날짜·종류 후보를 만든다. 모호한 항목은 사용자가 수정한다. 원문과 해석 결과를 함께 보여준다.

Any.do
WhatsApp 연동

채팅에서 할 일을 만들면 봇이 확인을 돌려준다. 메신저에서 알림을 받고 완료·미루기도 한다. 계정 연결은 번호 확인을 거친다.

WhatsApp 연동 안내

`접수됨`과 `PC 반영됨`을 나눠 회신한다. 완료 버튼의 결과도 TomaDesk 적용 뒤 회신한다. 허용된 개인 채팅만 받는다.

Skeddy
Telegram 봇

짧은 문장으로 알림을 만들고 Telegram에서 미루거나 완료한다. 복잡한 반복 설정은 Mini App 화면으로 분리한다.

Skeddy 공식 사이트

초기 Telegram 명령은 입력·오늘 조회·완료로 한정한다. 복잡한 반복·긴 메모 편집은 PC 또는 기존 모바일앱에서 처리한다.

Microsoft To Do
My Day

여러 목록의 일을 하루 집중 화면에 모은다. 하루 화면이 초기화되어도 미완료 항목은 원래 Tasks 목록에 남고 다음 날 제안된다.

My Day와 제안

`/today`는 원본을 복사하는 새 목록이 아니라 현재 일정·할 일의 읽기 화면으로 만든다. 날짜가 지나도 원본 항목이 사라지지 않게 한다.

Todoist
Calendar 연동

시간이 정해진 일을 별도 Todoist 달력에 표시하고 기존 작업과 연결된 이벤트만 동기화한다. 달력에 새 이벤트를 만들었다고 새 작업이 자동 생성되지는 않는다. 반복·삭제에도 예외가 있다.

Calendar 연동 안내

TomaDesk 전용 Google Calendar에 선택 일정만 내보내고 대응 ID를 보관한다. 역방향 수정은 실제 필요가 확인될 때 별도 설계한다.

공통 패턴: 빠른 포착 → 확정 전에 정리 → 같은 항목을 다른 화면에서 확인 → 조작 결과를 다시 알려줌. TomaDesk는 기존 Organizer가 있으므로 이 흐름을 작은 범위로 구현할 수 있다.
02 / TomaDesk에 가져올 것

채택할 경험과 지킬 경계

입력

수집함을 단일 관문으로

Telegram·추후 ChatGPT의 짧은 입력은 같은 Action 계약으로 들어간다. 해석은 TomaDesk Organizer 한 곳에서 하고, 원문과 메시지를 보낸 시각을 보존한다.

확인

두 번의 상태 통지

외부 저장 성공은 `접수됨`, DB 커밋 성공은 `반영됨`이다. PC가 꺼져 있으면 `검토 대기`를 표시한다. 중복 요청은 같은 결과를 다시 돌려준다.

조회

오늘 화면은 읽기 모델

일정·미완료 업무·D-Day를 Snapshot으로 묶는다. Telegram에서 보는 목록에는 마지막 PC 갱신 시각을 함께 넣는다.

조작

버튼은 Action을 보낸다

완료·미루기 버튼은 PC DB를 즉시 바꿨다고 표시하지 않는다. 적용 영수증이 온 뒤 결과 메시지와 버튼 상태를 갱신한다.

Calendar

전용 달력으로 좁게 시작

선택한 일정만 Google Calendar에 복제해 Samsung Calendar에서 본다. 외부 이벤트 ID와 TomaDesk ID 대응을 저장한다.

메모

긴 문서는 기존 앱으로

Telegram은 짧은 아이디어를 받는다. 현재 Organizer의 아이디어·정보는 수집 기록이므로 일반 메모 생성 경로를 추가한다. 리치 편집·첨부는 기존 Android 앱의 영역이다.

현재 코드 근거: alert_notes/memo_organizer.py, alert_notes/memo_organizer_store.py, mobile_bridge/service.py, docs/MOBILE_RELEASE_NOTES.md.

03 / 사용 흐름 시안 이미지

처음 사용할 때 보일 세 화면

아래 이미지는 구현 전 화면 시안이다. 메시지 문구·배치·색은 실사용 검증 뒤 조정할 수 있다. SVG로 직접 그려 HTML 안에 포함해 파일 하나만 열어도 보인다.

04 / 공통 구조

빠른 화면은 여러 개, 기준 데이터는 하나

Telegram은 선택적인 빠른 입력 채널이고, Drive는 Telegram 및 허용된 AI 채널의 전달·조회 저장소다. TomaDesk PC DB는 동기화 완료된 일정·할 일·메모의 기준이다. Android 앱의 개인 메모는 휴대폰 내부에 저장하고 PC에 직접 연결될 때만 동기화한다. Android 앱은 Telegram·Drive·Dot 없이도 사용 가능해야 한다.

Telegram문장·조회·버튼
↔
수신기 + DriveAction · Receipt · Snapshot
↔
TomaDesk PCOrganizer · 일정 · 메모 DB

Telegram → PC

  1. 1메시지 원문·전송 시각·출처 ID를 받아 Action 생성
  2. 2PC가 중복 여부 확인 후 Organizer 수집함에 표시
  3. 3사용자 검토와 DB 커밋 후 Receipt 작성·회신

PC → Telegram·허용 AI

  1. 1허용된 일정·할 일만 읽기용 Snapshot으로 생성
  2. 2업로드 성공 뒤 최신본 교체, 마지막 갱신 시각 기록
  3. 3Telegram 조회에 응답하고 AI에는 읽기 권한만 제공. 쓰기 제안은 새 Action 초안으로 접수
계약의 핵심 — `action_id`와 출처 이벤트 ID로 중복을 막고, Telegram 전송 시각으로 `내일`을 해석한다. Drive 파일 이동만으로 성공을 판정하지 않는다. DB 처리 영수증은 커밋과 함께 기록하고 Snapshot에는 생성 시각·버전을 넣는다.
추후 Android 앱 연동 결정 — PC가 꺼져 있거나 연결되지 않아도 메모 작성·수정·열람은 휴대폰의 로컬 저장소에서 계속된다. 미반영 변경은 기기 안에 보존하고, PC에 직접 연결 가능해지면 수동 또는 명시적인 재시도로 동기화한다. 연결 실패를 저장 실패로 표시하거나 임의로 변경을 삭제하지 않는다. 개인 메모 본문·첨부·동기화 대기열을 Telegram·Drive·기타 클라우드 중계에 올리지 않는다. 따라서 PC가 꺼진 동안 PC 반영 및 다른 기기와의 동기화는 불가능하다는 한계를 화면에 분명히 표시한다. PC DB와 모바일 변경이 동시에 달라졌다면 어느 쪽도 묵시적으로 덮어쓰지 않고 충돌 사본/선택 절차로 보존한다. 현재 QR·LAN 직접 연결을 기본 경로로 검증하고, 원격 직접 연결이 필요할 때만 별도 방식을 검토한다. 인증 없는 모바일 브리지 포트를 인터넷에 공개하지 않는다.
추후 배포 검토 · 선택형 클라우드 동기화 — 현재 작동하는 QR·LAN 직접 연결은 유지하고 클라우드 동기화를 지금 구현하거나 기본 경로로 바꾸지 않는다. 추후 배포 방향을 결정할 때, 사용자가 직접 연결 또는 클라우드 동기화를 명시적으로 선택할 수 있는 방안을 평가한다. 도입 전에는 계정 연결과 개인 메모·첨부의 클라우드 보관 동의, 저장 공간·운영 비용, PC가 꺼져 있을 때의 대기 및 재개, 양방향 변경 전송, 두 경로를 번갈아 쓸 때의 중복·revision·충돌 사본·첨부 보존을 검증한다. 클라우드 경로는 별도의 데이터 처리 결정이므로 채택 전까지 위의 클라우드 미전송 원칙을 유지한다.
AI 운영 계층 결정 — ChatGPT·Dot은 허용된 Snapshot의 독자이자 Action 초안 작성자다. Dot은 지속적인 상태 확인·브리핑 제안에 활용하되 PC DB, 동기화 엔진, 필수 인프라를 대체하지 않는다. Dot의 기억이나 분석 결과를 최신 원본으로 취급하지 않고, Android 앱에서 휴대폰에만 저장한 메모를 AI로 보내지 않는다.
05 / 개발 순서

작은 왕복을 완성한 뒤 넓힌다

FIRST LOOP · 0–3
입력 → 검토 → 반영

백업, Action, Telegram 수신, Organizer 승인. Dot 연결 가능성은 비차단 소규모 시험만 한다.

DAILY USE · 4–5
조회 → 완료 → 알림

Snapshot을 만들고 오늘 목록과 버튼을 붙인다. 마지막 갱신 시각을 표시한다.

CONNECTION · 6–8
Calendar → AI 계층

전용 달력 단방향 표시 후 ChatGPT·Dot 브리핑, AI Action 초안으로 확대한다.

AFTER USAGE · 9–10
모바일앱 → 고급 양방향

실제 사용 빈도를 보고 긴 메모·오프라인·충돌 처리에 투자한다.

9–10기존 모바일앱의 기기 내 저장·대기 변경·PC 직접 동기화 검증 및 고도화, 필요할 때 Calendar 역방향Telegram 없이 오프라인 편집 가능. PC 연결 복구 후 누락·중복·묵시적 덮어쓰기 없이 동기화되고, PC 미연결 상태가 명확히 표시됨.선택

1–4단계의 로컬 구현 범위와 아직 검증하지 못한 부분은 Hub 구현·검증 경계에 기록했다. 코드 추가만으로 실사용 완료를 선언하지 않는다.

기존 Android 앱과 모바일 브리지 코드는 이미 있다. 이 표의 9단계는 신규 앱을 처음부터 만들겠다는 뜻이 아니라 실제 기기 사용 결과를 바탕으로 기존 앱의 우선 개선 범위를 고른다는 뜻이다.

선택형 클라우드 동기화는 9단계의 확정 구현 범위가 아니다. 현재 직접 연결 사용 결과와 추후 배포 요구를 확인한 뒤 별도로 채택 여부·제공 범위·검증 기준을 결정한다.

초기 Dot PoC · 핵심 일정 비차단

계정에서 Dot을 사용할 수 있는지 확인하고, 연결 권한을 받은 Drive의 가짜 briefing.json과 선택 Calendar를 읽어 본다. 마지막 PC 갱신 시각을 브리핑에 표시하고, 제안과 실제 쓰기 권한이 분리되는지 확인한다. 실제 개인 메모는 올리지 않는다. 사용 불가·권한 부족이면 ChatGPT/예약 작업 경로를 유지한다.

AI 권한과 역할

ChatGPT는 요청 시 분석, Dot은 연결된 허용 자료의 지속 확인·후속 제안, 예약 작업은 정해진 시각의 실행을 맡는다. 모두 Snapshot만 읽고 Action 초안만 제안한다. PC DB 적용·중복·revision·충돌 판정은 TomaDesk가 담당한다. PC 로컬 파일 접근에는 온라인 PC와 열린 ChatGPT 앱이 필요하다.

06 / 구현 전 확인할 것

가장 먼저 수신 경로를 검증한다

초기 제안의 수정점. Telegram 공식 FAQ는 웹훅 리다이렉트를 지원하지 않는다고 한다. Google Apps Script Content Service는 반환 내용을 별도 주소로 리다이렉트한다. 따라서 Apps Script 웹앱을 Telegram 웹훅에 직접 연결하는 방식을 확정하지 않는다. 이 결론은 두 공식 문서를 조합한 설계상 우려이며, 실제 테스트로 판정한다. Telegram FAQ · Apps Script Content Service

수신 방식 A · Apps Script 주기 조회

시간 트리거가 Telegram getUpdates를 호출해 Drive에 저장한다. 별도 상시 PC 서버 없이 시작할 수 있다. 저장이 끝난 업데이트만 offset을 전진시키고, 지연·할당량·24시간 보관 한도를 측정한다.

MVP 우선 검토

수신 방식 B · HTTPS 중계 웹훅

직접 2xx 응답과 Telegram 비밀 헤더 검증이 가능한 중계 서버를 둔다. 즉시성은 좋지만 운영·인증·비용이 늘어난다. A의 지연이 사용성을 해칠 때 비교한다.

필요 시 검토
실제 DB 복원본에서 일정·메모·첨부·수집함을 확인한다.
허용 사용자 ID와 채팅 ID를 검사하고 비밀값을 로그에 남기지 않는다.
Telegram 업데이트 보관 시간과 스크립트 실행 실패를 감시한다.
`내일`은 웹훅/조회 시각이 아닌 메시지 전송 시각으로 해석한다.
민감한 본문은 외부로 내보내지 않는다. 초기에는 선택한 소수 항목만 공개한다.
PC가 꺼진 동안의 접수와 조회 화면의 오래된 데이터 표시는 분리한다.
1–2주 실사용에서 오분류·누락·중복·승인 소요를 기록한다.
Calendar는 먼저 전용 달력 단방향으로 시험하고 역방향은 나중에 결정한다.

Telegram 업데이트는 공식 문서상 24시간 넘게 보관되지 않는다. Apps Script 시간 트리거는 분 단위로 설정할 수 있지만 실제 지연과 무료 할당량은 운영 중 확인해야 한다. Bot API · 시간 트리거 · 할당량
