04 / 연결 방식 결정

직결 웹훅을 전제로 시작하지 않는다

공식 문서에서 확인한 제약: Telegram 웹훅은 리다이렉트를 지원하지 않는다. Apps Script Content Service는 응답을 script.googleusercontent.com으로 리다이렉트한다. 따라서 `Telegram → Apps Script doPost` 직결이 안정적으로 성공한다고 가정할 수 없다. 또한 Apps Script 웹앱 이벤트 문서의 필드에는 임의 요청 헤더가 제시되지 않아 Telegram의 비밀 헤더 검증도 전제하지 않는다. Telegram FAQ · Content Service · 웹앱 이벤트
방식동작과 장점제약판정
A. Apps Script 주기 조회시간 트리거가 getUpdates로 받는다. PC가 꺼져도 Drive에 입력을 저장할 수 있다. Bot 토큰으로 Telegram 서버를 직접 조회하므로 웹훅 요청 위조 문제가 없다.5분 간격이면 응답이 즉시 오지 않는다. 트리거 실패가 24시간 이상 지속되면 Telegram에 남은 업데이트가 사라질 수 있다.MVP 권장
B. HTTPS 웹훅 중계중계가 리다이렉트 없는 2xx 응답과 Telegram 비밀 헤더 검증을 처리하고 Drive 또는 Apps Script에 전달한다.별도 배포·자격 증명·운영 비용과 장애 지점이 생긴다.지연이 문제일 때
C. PC 직접 조회PC 앱이 켜져 있을 때 구현 경로가 단순하다.PC가 꺼지면 24시간 이후 입력을 놓칠 수 있어 이 계획의 오프라인 접수 목표와 맞지 않는다.주 경로로 제외

초기 트리거는 5분 주기와 짧은 양의 long polling으로 시험한다. 5분은 설계 시작값이며 즉시성 보장은 아니다. 실제 실행시간, 하루 90분 트리거 한도, URL Fetch 사용량과 사용자 체감 지연을 측정한 뒤 조정한다. Telegram getUpdates와 웹훅은 동시에 사용할 수 없으며 미확인 업데이트는 최대 24시간 보관된다. Bot API · 시간 트리거 · 할당량

수신기 처리 순서

  1. 1스크립트 잠금 획득, 저장한 Telegram offset 읽기
  2. 2업데이트를 순서대로 검증하고 Drive에 최소 JSON 저장
  3. 3연속해서 저장된 마지막 업데이트까지만 offset 전진
  4. 4접수 메시지 발송, 실패하면 별도 발송 대기 기록

회신기 처리 순서

  1. 1PC가 Drive Receipt 또는 알림 Outbox를 기록
  2. 2Apps Script가 전송 대상·내용을 검증하고 Bot API 호출
  3. 3성공하면 Telegram message_id와 전송 시각 기록
  4. 4전송 결과가 불명확한 재시도는 중복 메시지 가능성을 표시
05 / Action · Receipt · Snapshot

세 문서로 왕복을 추적한다

Drive는 전용 비공개 폴더에 작은 JSON을 저장한다. 파일명이나 폴더 이동만으로 적용 성공을 판단하지 않는다. 한 요청의 최종 상태는 PC DB 처리 영수증으로 판정한다.

  "received_at_utc": "2026-10-02T05:05:08Z",
  "base_timezone": "Asia/Seoul",

중복 기준

Telegram 이벤트 ID

같은 update_id 재수신은 동일 Action. 별도 메시지 두 건이 같은 문장이어도 서로 다른 입력이다. PC 적용은 고유 출처 ID와 Action ID로 한 번만 한다.

날짜 기준

보낸 시각

수신 지연이나 PC가 꺼진 시간을 고려해 `내일`은 메시지 전송 시각을 한국 시간으로 바꾼 날짜를 기준으로 해석한다. 수신 시각도 별도로 남긴다.

조회 기준

Snapshot 시각

/today 응답은 PC가 생성한 읽기 전용 Snapshot에서 만든다. 마지막 갱신 시각을 항상 쓰고, 오래된 경우 상단에 경고한다.

정확히 한 번의 범위: PC DB 변경은 동일 Action에 대해 한 번만 적용한다. Telegram sendMessage 호출의 응답이 끊긴 경우, 전송은 성공했는데 확인만 실패했을 수 있어 회신 메시지는 중복될 수 있다. 영수증과 전송 기록으로 이를 줄이고 DB 결과를 기준으로 안내한다.
06 / 기존 TomaDesk에 연결할 지점

Organizer를 재사용하려면 바꿔야 할 부분

현재 코드에서 확인한 사실Telegram 연결 작업검증할 것
OrganizerStore.capture(raw, base)는 같은 날 같은 원문이면 기존 capture ID를 돌려준다.외부 수집에는 출처 이벤트 ID를 부여한다. 같은 Telegram 업데이트만 재사용하고, 별도 메시지는 별도 수집 건으로 둔다.같은 문장 2회 전송과 같은 업데이트 2회 수신을 구분.
analyze()는 `3시`처럼 오전/오후가 모호한 입력을 확인 대상으로 둔다.Telegram에서 파싱하지 않고 원문·보낸 날짜를 Organizer에 넘긴다.날짜 경계, 상대 날짜, 확인 필요 후보를 PC에서 수정.
OrganizerStore.apply()는 일정·날짜 있는 할 일을 schedule_items에 저장한다. 아이디어·정보는 수집 기록에 남는다.일반 메모로 선택했을 때 메모 목록에 새 메모를 만드는 명시적 경로를 추가한다. 승인과 Action 영수증은 DB 트랜잭션으로 묶는다.메모 생성·일정 생성·거부·부분 선택의 결과가 맞음.
schedule_items의 기본 ID는 로컬 정수다.Snapshot·버튼에는 안정적인 외부 ID와 버전 매핑을 만든다. 로컬 정수 ID를 Telegram에 그대로 노출하지 않는다.일정 수정·삭제·DB 복원·오래된 버튼을 안전하게 처리.
기존 Android 브리지는 메모 동기화와 별도의 mobile_receipts를 사용한다.Telegram 영수증을 별도 네임스페이스로 두고, 메모 변경 시 기존 충돌 규칙과 중복 적용을 확인한다.모바일 편집과 Telegram 입력이 같은 메모에 닿는 경우.

코드 근거: alert_notes/memo_organizer.py, memo_organizer_store.py, memo_organizer_panel.py, schedule_store.py, mobile_bridge/service.py. 실제 사용자 DB를 변경하기 전 백업·복원본에서 마이그레이션을 검증한다.

07 / 연결·보안·운영

개인 봇답게 연결 범위를 작게 둔다

연결

PC에서 1회 코드 발급

PC 연결창이 짧은 수명의 1회 코드를 표시하고, 코드 해시·만료시각을 전용 Drive 연결 설정에 기록한다. 사용자 본인이 Telegram 개인 채팅에 /pair 코드를 보내면 Apps Script가 해시와 만료시각을 확인하고 코드를 소진한다. 성공한 숫자 user ID와 chat ID만 허용 목록에 남긴다.

자격 증명

토큰은 설정 저장소에

Bot 토큰은 Apps Script Script Properties에 보관하고 Git·일반 로그·Drive Action에는 쓰지 않는다. Script Properties는 스크립트 편집자와 공유되므로 편집 권한도 개인 계정으로 제한한다.

Drive

전용 비공개 폴더

incoming/, receipts/, snapshots/, outbox/를 분리한다. Apps Script와 PC가 같은 계정·폴더에 접근하는지 먼저 확인한다. 공개 링크는 만들지 않는다.

개인정보

짧은 제목만

주민등록번호·행정자료 전문·의료정보·첨부·긴 메모 본문은 Telegram과 Snapshot에서 제외한다. local_only 정책이 실제 저장·내보내기 전 경로에 적용되는지 검증한다.

버튼

오래된 클릭 거부

callback에는 64바이트 이내의 짧은 ID·행동·버전만 넣는다. 5분 주기 조회에서는 클릭 응답이 늦을 수 있으므로, 버튼 단계 전에 실제 지연을 측정하고 필요하면 HTTPS 웹훅 중계로 바꾼다. 수신 즉시 접수 응답을 보내고 PC가 버전 충돌을 확인한다.

관찰

조용한 실패 방지

마지막 성공 poll, Telegram 미확인 건수, Drive 저장 실패, PC 마지막 동기화, Outbox 실패를 상태 화면에 표시한다. 24시간 넘는 수신 중단은 데이터 손실 가능성으로 경고한다.

Telegram 버튼은 callback_data 1–64바이트 제한이 있고, 클릭 뒤 answerCallbackQuery를 호출해야 진행 표시가 멈춘다. 버튼 규격 · 클릭 응답 · Script Properties · Script Lock

08 / 개발 단위와 합격 기준

먼저 연결하고, 실제 쓰면서 넓힌다

T0 · 안전·실험

DB 백업·복원, 수신 방식 A 시험, Telegram 봇 생성·계정 연결 설계, Drive 권한 확인

실제 봇 테스트에서 PC를 꺼도 메시지가 Drive에 남고, 중복·누락·지연과 트리거 실행시간을 기록한다.

T1 · 입력

Apps Script 수신기, 개인 chat 허용 목록, 텍스트 검증, Action 저장, 접수 응답

같은 업데이트 재수신 시 PC 반영 0건 중복; 별도 메시지 두 건은 두 건으로 수집.

T2 · PC 검토

Organizer 외부 출처 표시, 메모 생성 경로, 승인·거부, 로컬 영수증과 Drive Receipt

원문·전송 날짜를 보존하고 일정/할 일/메모가 승인 뒤 정확히 반영된다.

T3 · 결과 회신

Apps Script Outbox, 반영·거부·오류 회신, /status

PC 오프라인 동안 `검토 대기`, 재개 후 최종 결과. 발송 실패는 재시도와 가시적 기록.

T4 · 조회

허용 Snapshot, /today·/task·/dday, 마지막 PC 갱신 시각

민감 항목 제외, 최신본 교체 실패 시 직전 성공본과 오래됨 표시.

T5 · 버튼·알림

버튼 응답 지연을 먼저 측정하고 필요하면 HTTPS 중계로 전환한 뒤 완료·내일로, 제한된 알림·미루기, 오래된 버튼/버전 처리

버튼의 접수 응답이 실사용 가능한 속도로 표시되고, 연타·중복 callback·PC 꺼짐·동시 PC 수정에도 최종 상태가 일치.

첫 실사용 판정: T0–T3 후 실제 휴대폰에서 짧은 문장 1건을 보내 PC 수집함에서 검토·승인하고, Telegram에 최종 결과가 돌아오는 왕복을 확인한다. 이후 1–2주 동안 사용 건수·오분류·승인 소요·누락·중복·사용자가 누른 다음 동작을 기록해 T4–T5의 우선순위를 조정한다.

필수 검증 시나리오

PC 종료 중 보낸 메시지가 재실행 후 수집함에 도착한다.
Apps Script 중단 뒤 재시작해도 이미 처리한 메시지가 다시 적용되지 않는다.
동일 문장을 두 번 보내면 두 입력으로 보이고 중복 등록은 승인 시 확인한다.
같은 Telegram update를 두 번 받아도 Action과 DB 결과는 한 건이다.
`내일 3시 병원`은 보낸 날 기준으로 해석하고 시각은 확인 필요로 남는다.
허용되지 않은 계정·그룹 메시지·파일·음성은 안전하게 거절한다.
Receipt 발행 실패·Bot 전송 타임아웃 뒤 복구한다.
오래된 완료 버튼과 DB 복원 후 버튼은 적용하지 않고 새 조회를 안내한다.
Snapshot에서 비공개 항목과 긴 메모 본문이 제외된다.
실제 사용자 DB는 복원본 검증 뒤에만 연결한다.
